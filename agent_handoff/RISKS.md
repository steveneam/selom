| 10 | **`gsea` (gseapy.prerank) is markedly less sensitive than fgsea** | At the same ranking + gene sets, gseapy.prerank calls **far fewer** significant terms than the authors' fgsea — surfaced in the RPGRIP1 Fig-6E dogfood: on identical Cepo rankings over MSigDB C5, gseapy = 24/36/1 enriched GO terms per rod subtype vs **fgsea = 62/95/85** (the paper's totals are 102/119/74). Term-count-based panels (GO-term Venns, "N enriched pathways") will under-reproduce. | The gsea skill already has a **`blitzgsea`** engine (Apache-2.0, gamma-fit p-values "closest to fgsea for tiny q") but it's opt-in (its first-import numba JIT timed out in dev). **Pre-ship:** make blitzgsea selectable/fast on a deploy box, or add an fgsea-equivalent multilevel p-value path; document gseapy's conservatism for term-count claims. Not a correctness bug — a sensitivity gap. | Claude (BE) |
| 11 | **Stub engine can serve fabricated figures as HTTP 200** | Every skill falls back to a dependency-free *synthetic* figure when `use_real_engine()` is false (deps missing under `auto`, or `SELOM_SKILLS_ENGINE=stub`). A deploy missing the scverse/pydeseq2 extras — or one left on stub — would ship **fake science** with only a faint "(stub)" title: a direct breach of the "no black box" promise. | **GUARD SHIPPED (WS1.1, 2026-07-02):** (a) a **prod boot guard** (`config.Settings._validate_backend_combos` + `is_production`) makes the engine unable to resolve to stub off-dev — in production (`SELOM_ENV=prod`, or a live Clerk auth / S3 store) a forced-stub or a missing science extra **fails loud at startup**, not per-request; (b) provenance stamps the **RESOLVED** policy (`skills/_engine.resolve_engine_policy` → `"real"`/`"stub"`), and any stub figure that *does* render (dev/canned-demo) carries a prominent FE **"example data — not your results"** banner (`components/project/stub-engine-banner.tsx`); (c) `test_engine_policy_guard.py` proves the stub is unreachable with extras present + a drift-guard keeps `REQUIRED_ENGINE_MODULES` a complete mirror of every skill's real-engine gate. Stubs stay legit for dev/demo/tests (never deleted, only guarded + labelled). | Claude (BE+FE) |
| 12 | **FlowKit ⊥ pandas 3.0** (the `facs_gating` skill) | FlowKit (the flow-cytometry engine) hard-pins `pandas<3,>=2.2`, incompatible with this backend's `pandas>=3.0` — the same class as OmicVerse (#9). It **cannot** live in the shared venv: added as a `REQUIRED_ENGINE_MODULE` it drags the WHOLE engine to `stub` on every box (flowkit missing everywhere) **and refuses prod boot**. Secondary honesty gap: a per-skill-`find_spec`-gated skill that stubs in prod is NOT caught by the WS1.1 prod-boot guard (which only checks `REQUIRED_ENGINE_MODULES`), so a FACS stub in a global-`real` context ships with only the faint "(stub)" title, not the "example data" banner. | **RESOLVED 2026-07-23 — clean-room in-process engine (no FlowKit, no sidecar).** FlowKit's genuinely-hard parts are SEPARATE BSD-3, numpy-only packages that run on pandas 3.0: FCS parsing (**FlowIO**) + compensation & the logicle/arcsinh/log transforms (**FlowUtils**, C-accelerated). Only FlowKit's thin top (gate-tree + population report) pins `pandas<3`, and that is just numpy geometry + counting — reimplemented in `skills/facs_gating/run_real.py` (rect/polygon/quadrant membership in transformed display space + population stats; the Melody↔Harmony clean-room pattern). So `facs_gating` runs **REAL, IN-PROCESS, on pandas 3.0** — flowio+flowutils are now in `REQUIRED_ENGINE_MODULES` + the `flow`/`omics` extras, making it a **first-class engine-gated skill**, so the WS1.1 prod boot guard + honest provenance cover it — closing BOTH the acute pandas conflict AND the secondary honesty gap. FlowKit is no longer a dependency (its bokeh/tornado transitives dropped from `uv.lock`). Verified: 11 real-engine smoke tests + 12 engine-policy guard tests green. **Supersedes** the out-of-process-worker plan in `docs/facs-prod-integration/spec.md`. | Claude (BE) — DONE |
